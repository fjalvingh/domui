## Goal

Bring the documentation and the demo/tutorial application back in line with the
framework as it is today, and remove old and incorrect code and information.
Concretely:

1. **Documentation must be true.** Everything on the site should describe the
   current code (Java 21, Jakarta EE, Hibernate 7.2, `skarp-master`), not the
   2017-2018 Confluence-era state it was converted from.
2. **The demo must be a good tutorial.** The demo application is the primary way
   people learn DomUI; its pages should show the *recommended* way to do things,
   not every historical way.
3. **Dead weight goes.** Obsolete components, superseded APIs, dead demo pages
   and pages documenting things that no longer exist are removed rather than
   left to mislead.

## Guiding principle: current version, current usage

**The documentation and the demo describe DomUI as it is now, and the one way it
is meant to be used now. Nothing else.**

This is decided (see the decisions log in `IMPROVEMENT-LOG.md`) and is not to be
re-opened per page:

- Historic information is **removed, skipped, or rewritten to state the current
  truth** - whichever of the three fits. It is never kept "for context".
- No version history, no "this used to be X", no "since DomUI 2.0", no migration
  notes from superseded APIs, no parallel documentation of an old and a new way
  of doing the same thing.
- Where two generations of an API exist (`component` vs `component2`, old form
  builders vs `form4`, old lookup vs `lookupinput`), the docs and the demo show
  **only the current one**. The older one is not documented, not demonstrated,
  and - once nothing depends on it - not kept.
- A page whose entire subject is historic is deleted, not updated.

### Defects known and deliberately left alone

Raised while writing the component pages, looked at, and decided against acting on
for now. They are recorded so they are not re-discovered as news.

- IGNORE: **`CKEditor.setToolbarSet()` throws its own javascript away.** On a built
  editor it composes the statement that would set the new toolbar and then calls
  `appendJavascript("")` - the empty string, not the statement. Repairing that
  would not help much: assigning `.toolbar` on a live CKEditor 4 instance does
  not redraw its toolbar either. The honest fix is to drop the dead branch and
  let the setter be a build-time property. (Found writing the group 11 pages.)

- IGNORE: **`CKEditor` can never set its own width and height.** The `setWidth()` and
  `setHeight()` overrides are commented out, so `m_internalWidth` and
  `m_internalHeight` stay null and the `width:`/`height:` options are never
  emitted into the editor's configuration. The calls size the wrapping `div`
  instead, which is not the same thing - the toolbar eats the height.

- IGNORE: **CKEditor 4.3 is bundled**, dating from 2013, and CKEditor 4 is out of
  support. `DomApplication` already stopped loading it on every page for that
  reason. Deciding what happens to it - upgrade, replace, or keep as an
  opt-in - is worth doing deliberately rather than by neglect.

- IGNORE: `ImageSelectControl`'s accepted types (`.jpg,.jpeg,.png,.gif`) and its 10MB
  limit are hardcoded in `createContent()`, where `FileUpload2` makes both
  properties.

- IGNORE: `RadioGroup` has three overlapping enum factories: `createEnumRadioGroup(Class,
  exceptions...)` (sorted), `createEnumRadioGroupUnsorted(...)` and
  `createFromEnum(Class, ignored...)` - the last being a duplicate of the second.
  Only the first two are documented; `createFromEnum` is a candidate for removal.

- IGNORE: DomUI's own message bundles have **Dutch** as their default language: the
  base `to/etc/domui/util/messages.properties`, `YesNoType.properties`,
  `MsgBoxButton.properties` and the rest are Dutch, with English in the `_en`
  files. Any user whose locale has no bundle of its own therefore gets Dutch
  framework texts. Swap the two files around so the base language is English?

## Working agreements

- Documentation changes go in `/home/jal/git/update-domui/domui.github.io`, code and demo
  changes in `/home/jal/git/update-domui/domui`. A single logical improvement often needs a
  commit in both; mention the counterpart in each commit message.
- Prefer deleting over marking "obsolete". A page or demo that is wrong does more
  damage than a missing one.
- When a doc statement cannot be verified against the source, verify it by
  running the demo rather than guessing.
- Keep the two files updated: an item finished here moves to `IMPROVEMENT-LOG.md`
  with what it did and what was verified, and what it decided goes in that file's
  decisions log, so later sessions do not re-litigate it. This file stays a list of
  what is still to do.
